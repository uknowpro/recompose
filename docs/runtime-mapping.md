# Runtime mapping

Extraction reconciles a single Compose service with an OCI image without executing it. Compose `entrypoint: null` and `command: null` inherit image settings. A non-null entrypoint clears the image command; a non-null command then replaces it. Empty lists and empty strings explicitly clear their respective settings. Strings are split into arguments without shell evaluation. Multiple Compose files, interpolation, includes and extends are not resolved.

Recognized direct `java -jar` arguments include heap/stack sizes, numeric/boolean `-XX` options, a small set of encoding/timezone/profile properties, Java agents, explicit native agents, `java.library.path`, `loader.path`, Spring configuration locations, logging configuration and `--server.port`. Unknown values are omitted with a blocking review item rather than exposed in reports. Arbitrary arguments can be supplied manually in the reviewed plan.

Referenced image files keep their image-relative layout beneath `/opt/<service>/rootfs`. The main JAR and working directory use the same mapping. This preserves relative paths but cannot rewrite paths embedded inside application code or configuration. Implicit Spring configuration discovery, transitive native dependencies, dynamic downloads, and manifest Class-Path resolution are not implemented. Use repeated `--include-file` options for additional known files. Native files and agents require compatibility review before marking each file reviewed.

The layer reader applies whiteouts and opaque directories, rejects traversal, and never follows image links. It retains at most 256 file candidates across all layers, under the existing image size limits. A requested file hidden by a Compose volume is not taken from the image. Host files, volume data, Compose secrets/configs and env files are not read. Likely secret files are omitted; this heuristic is not a complete secret scanner. Unknown application/JVM values and environment values are excluded from reports. Paths, recognized options and file names remain visible.

`files` entries record a local source, managed VM destination, SHA-256, role and review status. Generation requires each file to be reviewed, remain inside the plan directory, match its checksum and target the service's rootfs directory without collisions. Supplemental files are installed root-owned, service-group-readable (`0640`), with Ansible diff output disabled. The working directory is service-owned; review application write requirements. Resolve every finding and review the top-level plan before generating. These gates record operator decisions; they do not verify application compatibility.

The host CLI architecture and destination VM architecture are independent. The selected image `--platform` defaults to `linux/amd64`; select `linux/arm64` for ARM image extraction. Confirm the destination matches any native library architecture. Actual VM start, health checks, OS dependency mapping and rollback remain separate validation work.

References: [Compose service command](https://docs.docker.com/reference/compose-file/services/#command), [Compose entrypoint](https://docs.docker.com/reference/compose-file/services/#entrypoint), [Java launcher](https://docs.oracle.com/en/java/javase/21/docs/specs/man/java.html).
